# Ревью реализации Kart Racing Display

Дата: 2026-10-08. Проверено текущее содержимое рабочей директории, включая
незакоммиченные файлы. Это отчёт и план исправлений: рабочий код не изменялся.
Номера строк относятся к версии на дату ревью.

## Вывод

Модульная основа подходит для проекта: небольшой общий store в памяти, явная
сборка модулей в `run.py`, отделённый экранный планировщик, кеширование GIF.
База данных и отдельный брокер сообщений сейчас не нужны.

Основные проблемы — корректность граничных данных и устойчивость длительной
работы. Веб-клиент не согласован с новым протоколом обновлений; отсутствие кругов
подменяется нулевым кругом; ошибки отдельных обработчиков и источников могут
останавливать потоки; устаревшие показания продолжают выглядеть актуальными.
Сначала следует устранить P1, затем укреплять lifecycle и оптимизировать экраны.

Приоритеты:

- **P1:** неверные результаты или потеря основного рабочего функционала; исправить первыми.
- **P2:** надёжность, соблюдение контракта, ресурсы и эксплуатация; следующий этап.
- **P3:** сопровождение и диагностика; после функциональных исправлений.

«Воспроизведено» означает отдельную диагностическую проверку. «По коду» означает
вывод из соответствующей ветки реализации, без утверждения, что сбой наблюдался
на подключённом оборудовании.

## Что проверено

Просмотрены ядро, источники файлов/TCP/RS-232/ODTEMP/часов, Pygame-композитор,
Flask-маршруты и клиентские шаблоны, настройки, журналирование, COM-инвентаризация,
Delphi-отправитель, существующие тесты и `interface.md`.

Результаты штатных тестов:

- Behave: 6 features, 44 сценария, 167 шагов — успешно.
- `unittest discover -s tests -v`: 2 теста — успешно.
- `unittest -v test_tcp_race_contract.py`: 1 тест — успешно.

Дополнительные проверки выполнялись с отдельными in-memory runtime, Flask test
client и TCP-сервером на свободном loopback-порту. Перечисление USB и ответы
ODTEMP подменялись. Реальный COM12 не открывался; USB не переподключался.
Не проверены настоящие SDL2-окна на трёх дисплеях, нагрузка на целевом ПК и сборка
Delphi 7. Успешные штатные тесты не подтверждают эти сценарии.

## P1: исправить первыми

### CR-01. Веб-страницы используют старый протокол обновлений

Места: `app/routes.py:91`, `app/templates/results.html:356`,
`app/templates/results_alt.html:265`, `app/templates/current_race.html:55`.

Шаблоны вызывают `/check-updates` без `revision`. Сервер принимает это как ревизию
0 и при наличии любых данных постоянно возвращает `updated:true`. Два одинаковых
запроса без изменения store воспроизведённо вернули `{revision:1, updated:true}`.
Клиент назначает перезагрузку через 800 мс. Часы также обновляют общий store каждую
секунду, хотя это не обязательно повод заново загружать таблицу гонки.

Дополнительно по коду:

- `сurrent_race.UPD_TIME` содержит кириллическую `с` и не объявлен в JavaScript;
  таймеры попадают в обработку ошибки вместо штатного режима.
- Два шаблона используют `data.timestamp`, отсутствующий в ответе сервера.
- `current_race.html:51,93` сравнивает `current_view` (`race`) с веб-подвидом
  (`style1`/`style2`), поэтому может перезагружаться без изменения состояния.

Рекомендация: вынести polling в один JS-модуль; передавать и сохранять ревизию,
не запускать несколько параллельных циклов, явно передавать интервал через JSON.
Разделить события изменения таблицы гонки и обновления часов/температуры.
Для `/state` использовать один и тот же enum и сериализацию Jinja `tojson`.
Либо вернуть timestamp в контракт, либо удалить его использование на клиенте.

Приёмка: браузер без новых данных гонки не перезагружается; новый круг и смена
подвида обновляют страницу однократно; в консоли нет ReferenceError/Invalid Date.

### CR-02. Участник без кругов получает фиктивный лучший круг 0 секунд

Место: `karting/modules/files.py:80`, `normalize_race()`.

Воспроизведено: `laps={"7":[],"12":[31.2]}` превращается в
`{"7":[0],"12":[31.2]}`. Карт 7 получает один круг, лучший круг 0 и первое место.
Это нормальная ситуация начала гонки, а не ошибочный входной снимок.

Рекомендация: сохранять пустые массивы, выставлять `total_laps=0`, неизвестные
времена — `None`; считать минимум только по реально завершённым кругам. Участников
без кругов показывать отдельно либо после участников с результатом. Обновить
шаблоны для `None`, не подменять отсутствие результата числом.

Приёмка: начало гонки со всеми пустыми массивами и добавление первого круга не
создают нулевых рекордов, не вызывают исключений и корректно меняют позиции.

### CR-03. Входные данные не проверяются по опубликованному контракту

Места: `karting/modules/tcp.py:25`, `karting/modules/files.py:80`,
`karting/modules/serial.py:42`, `interface.md`, разделы 2, 4–8.

Воспроизведено: TCP принимает `{"category":"records_day"}` без `data`, сохраняет
`None` и отвечает `ok:true`. Принимается также температура `NaN`.
По коду не проверяются обязательные поля гонки, допустимое состояние, совпадение
ключей participants/laps, типы и конечность времени кругов, структура рекордов.
Неверные значения могут заменить исправный снимок или вызвать ошибку вычислений.

Рекомендация: общий слой моделей/валидаторов категорий до записи в store.
Отдельные адаптеры совместимости для старого YAML и контрактного JSON; расчёт
гонки вынести из файлового источника в общий модуль. Проверять UTF-8, конечные
числа, допустимые значения и лимиты коллекций. Неизвестные категории разрешать
через явную регистрацию, сохраняя возможность расширения проекта.
При ошибке возвращать `ok:false` с понятным полем/причиной и сохранять прежний
снимок. Не объявлять обязательную валидацию реализованной только на основании
успешного приёма одного корректного сообщения.

Приёмка: отсутствующее data, неподдерживаемая версия, неправильные laps,
NaN/Infinity, несовпадающие участники и некорректные рекорды отклоняются;
корректные `null` для отсутствующих рекордов и пустые круги принимаются.

### CR-04. Ошибка подписчика срывает доставку события и может остановить источник

Места: `karting/core.py:49`, `EventBus.publish()`, `DataStore.set():84`.

Воспроизведено: исключение подписчика `data.test` пробрасывается из `set()`.
Значение уже записано, но `data.changed` не публикуется. Последующие подписчики
не получают событие. В файловом/часовом потоке такая ошибка не изолирована,
а в TCP подтверждение зависит от типа исключения, хотя запись уже совершилась.

Рекомендация: определить явную семантику «запись принята» и отделить её от
уведомлений. Исключение наблюдателя логировать с topic/source/handler, продолжать
доставку остальным и отражать сбой в здоровье модуля. Дорогую работу выполнять
через ограниченную очередь, не в callback источника. Не держать lock store
во время вызова сторонних обработчиков. При необходимости fail-fast оставить
его отдельным режимом тестов, а не поведением эксплуатационной шины.

Приёмка: падающий и медленный подписчики не прекращают работу источников;
остальные получают событие; TCP не сообщает отказ после уже принятой записи.

### CR-05. Ошибка автоопределения ODTEMP завершает поток без повторных попыток

Место: `karting/modules/odtemp.py:83`, вызов `list_ports.comports()` перед `try`.

Воспроизведено с подменой: `OSError` перечисления портов выходит из `_run()`.
Реальные ошибки открытия/чтения обрабатываются, но эта часть автодетекта не
попадает в цикл восстановления. Это нарушает требование повторять инициализацию
каждую минуту до успеха, пока модуль включён.

Рекомендация: весь цикл обнаружения, открытия и инициализации охватить обработкой
ожидаемых ошибок устройства/ОС. Публиковать состояние unavailable/reconnecting,
ждать через stop-event и снова выполнять полный автодетект. Не маскировать
неожиданные программные ошибки бесконечным catch: сообщать о них supervisor.

Приёмка: перечисление портов временно падает, затем возвращает устройство;
поток остаётся работоспособным, выполняет повторную попытку и логирует
восстановление только после нового измерения.

### CR-06. После потери термометра отображается старое значение как текущее

Места: `karting/modules/odtemp.py:155`, `karting/modules/screens.py:69`.

По коду при потере связи удаляется только `odtemp_device`; `temperature` и
`humidity` сохраняются. Планировщик берёт значение без проверки updated_at или
статуса источника. Число на экране может оставаться прежним неограниченно долго.
Если новая строка не содержит влажности, старая влажность также остаётся.

Рекомендация: хранить последнюю измеренную величину вместе со статусом качества
и временем получения; после watchdog отмечать stale/unavailable и показывать
«—»/«нет связи». При желании оставлять последнее число отдельно, с явной меткой
«последнее измерение». Учитывать владельца значения: потеря ODTEMP не должна
удалять свежую температуру, уже полученную от другого источника.

Приёмка: через 120 секунд без валидного измерения индикация перестаёт выдавать
старое число за текущее; после восстановления вновь показывается новое значение.

### CR-07. Сбой сканирования файлов может навсегда остановить сбор данных

Места: `karting/modules/files.py:40,44`.

По коду `iterdir()`, поиск новейшего файла и `stat()` выполняются вне защищённого
чтения. Файл может исчезнуть между glob и stat, а каталог — стать недоступным.
Исключение уходит из worker. Ошибки типов при нормализации также не входят в
существующий обработчик `OSError/yaml.YAMLError`.

Рекомендация: обрабатывать временную недоступность корня и отдельной категории,
пропускать исчезнувшие кандидаты, сохранять последнюю валидную версию и продолжать
следующее сканирование. Для производителей файлов договориться об атомарной
публикации: временный файл и rename. Чтение UTF-8 не должно молча игнорировать
повреждённые байты. Валидировать снимок до замены предыдущего.

Приёмка: удаление файла в момент сканирования, частично записанный YAML и
временная недоступность каталога не завершают worker; после исправления файла
новый снимок автоматически появляется. Уточнить политику: при ошибке новейшего
файла сохранять предыдущие данные или искать предыдущий валидный файл.

## P2: надёжность и завершённость реализации

### CR-08. Вложенные данные обходят блокировку, ревизии и события store

Место: `karting/core.py:84,94,99,110`.

Воспроизведено: `store.snapshot()['nested']['laps'].append(0)` меняет внутренний
store без увеличения revision. То же возможно через исходный объект после set,
через get и через payload события. `frozen=True` защищает оболочку DataValue,
а не вложенные dict/list. Доступ всех модулей ко всем данным этому не препятствует.

Рекомендация: выбрать единое правило immutable snapshots. Для небольших данных
достаточно defensive deepcopy на входе/выходе либо неизменяемых моделей.
Снимок нескольких категорий с метаданными получать атомарно под одним lock.
Изменения разрешать только через API store; документировать это правило.

Приёмка: изменение объекта, переданного в set или возвращённого из get/snapshot,
не меняет хранилище; параллельные чтения видят согласованный снимок.

### CR-09. Ревизия удаления и ожидание веб-обновлений некорректны

Места: `karting/core.py:103`, `app/routes.py:91`.

Воспроизведено: после set ревизий 1 и 2 и удаления второй категории сервер
возвращает revision 1; клиент с revision 2 получает `updated:false`.
Удаление не увеличивает глобальную ревизию и публикует только `data.removed`,
тогда как веб подписан на `data.changed`.
По коду также есть окно между проверкой revision и входом в Condition.wait:
изменение в этом окне теряет уведомление; ожидание не перепроверяет predicate.

Рекомендация: публичная монотонная ревизия store, увеличиваемая на set/remove;
единый change-event с операцией и revision. Атомарный API snapshot-with-revision
и wait-for-revision с циклом проверки predicate/deadline. Condition, состояние
подвида и подписки привязать к конкретному runtime/app, а не глобальным объектам
и набору id; подписываться при создании приложения, отписываться при закрытии.

Приёмка: удаление будит клиента и повышает ревизию; конкурентное изменение
между проверкой и ожиданием не приводит к лишнему ожиданию 30 секунд;
два Flask-приложения не влияют на состояние друг друга.

### CR-10. Runtime не гарантирует очистку и не контролирует жизнь модулей

Места: `karting/core.py:133,148`, `run.py:51`, stop/start фоновых модулей.

По коду ошибка одного stop прерывает очистку остальных. При частичном сбое start
текущий модуль не входит в список rollback. Повторные start/stop не имеют общей
семантики. После аварийного выхода worker основной runtime продолжает считаться
работающим. Некоторые stop логируют «stopped» после join(timeout), не проверяя,
завершился ли поток; повторный start способен создать второй worker.

Рекомендация: состояния stopped/starting/running/degraded/stopping/failed,
учёт успешно запущенных модулей, cleanup частичного start и независимая остановка
каждого модуля с накоплением ошибок. Обязательные и необязательные модули
различать явно. Завершение процесса обернуть в try/finally; atexit оставить
страховкой. Добавить health snapshot/API и оповещение о смерти worker.

Приёмка: отказ любого start/stop освобождает остальные ресурсы; повторный запуск
не дублирует потоки; зависший worker не получает ложный статус stopped.

### CR-11. TCP продолжает изменять данные после stop и не ограничивает клиентов

Места: `karting/modules/tcp.py:16,45,67`.

Воспроизведено: уже подключённый клиент после `TcpJsonSource.stop()` отправил
температуру 99, получил `ok:true`, и store обновился. shutdown/server_close
закрывают приём новых соединений, но существующие daemon-handler продолжают жить.
По коду отсутствуют idle timeout и предел одновременно обслуживаемых клиентов.
Лимит строки 1 MiB не ограничивает число потоков или общий размер store.

Рекомендация: отслеживать активные подключения, закрывать их при stop,
прекращать запись после перехода в stopping. Ввести таймауты, лимит клиентов,
размеров снимка/коллекций и зарегистрированных категорий. Disconnect логировать
через finally, включая ошибки чтения/записи. Если слушать `0.0.0.0`, отдельно
задать разрешённых отправителей/защиту сети: сейчас доступный клиент может
переписать общие категории. На localhost эта угроза менее существенна.

Приёмка: после stop ни один старый клиент не меняет store; незавершённая строка
и простаивающие соединения не удерживают ресурсы бесконечно.

### CR-12. Инициализация и выбор ODTEMP требуют дополнительных проверок

Места: `karting/modules/odtemp.py:15,174,199`.

Воспроизведено: ответы `~F0`, затем `~F0` после команды включения возвращают 0
как успешный период. По коду существующий положительный период принимается
независимо от watchdog: устройство с периодом больше 120 секунд будет постоянно
считаться неисправным. Выбор первого VID/PID неоднозначен для двух термометров.
Командное ожидание не проверяет stop-event и не логирует полученные строки;
readline с таймаутом не сохраняет незавершённую строку для следующего чтения.

Рекомендация: проверять подтверждённый положительный период и его соотношение
с watchdog; при необходимости перенастраивать. Выбирать по serial_number,
а при нескольких совпадениях без идентификатора сообщать неоднозначность.
Общий ограниченный буфер строк, stop-aware ожидания команд и DEBUG для всех
ответов и отброшенных строк. Успех инициализации отделять от успеха измерения.

Приёмка: нулевой/неверный период не признаётся рабочим; две одинаковые модели
различаются по настроенному серийному номеру; разбитая строка измерения
собирается; остановка во время инициализации имеет ограниченное время.

### CR-13. Обычный RS-232 не восстанавливается и обходит общий адаптер

Место: `karting/modules/serial.py:25,36`.

По коду ошибка открытия прерывает запуск runtime, а ошибка readline после
отключения устройства завершает worker без повторного подключения. JSON любой
некатегоризированной формы может стать температурой. Категория current_race
не нормализуется, в отличие от TCP и YAML.

Рекомендация: общий контрактный ingestion API из CR-03, политика reconnect
для serial и публикация здоровья источника. Автодетект задавать по ID, если
оборудование это позволяет; при фиксированном порте сохранять явный режим.
Не разрешать SERIAL_PORT и ODTEMP одновременно владеть одним COM-портом.

Приёмка: отключение/возврат RS-232 восстанавливает работу; один и тот же снимок
гонки через TCP и serial даёт одинаковое внутреннее представление.

### CR-14. Отсутствующие и устаревшие рекорды отображаются неправильно

Места: `karting/modules/screens.py:69,105,119`, `interface.md`, разделы 5–6.

Воспроизведено: `format_record(None)` возвращает строку `None`; это штатное
значение контракта для отсутствующего результата, которое попадёт на экран.
По коду date/month не участвуют в выборе актуальности: вчерашний records_day
может показываться как сегодняшний при отсутствии новых данных.

Рекомендация: форматировать отсутствие результата как «—»/«Нет результата»;
проверять дату дня и месяц в согласованном часовом поясе картинг-центра.
Старую статистику можно сохранить для диагностики, но не показывать под текущим
заголовком. Уточнить отдельные правила TTL для температуры, состояния гонки,
рекордов и постоянных рекламных текстов, а не один TTL для всех категорий.

Приёмка: null не выводится как Python None; после полуночи и начала месяца
предыдущий период не обозначается текущим, даже если отправитель отключён.

### CR-15. Частичная инициализация Pygame не защищена очисткой ресурсов

Место: `karting/modules/screens.py:193`, создание окон до `try` на строке 262.

По коду при отказе второго окна/renderer или создания texture уже созданные
ресурсы обходят блок finally с window.destroy/pygame.quit. `_cleanup_failed_start`
не ждёт завершения GUI-потока. После старта авария экранного worker только
логируется; веб может продолжать работать при фактически погасших экранах.

Рекомендация: try/finally должен охватывать pygame.init и весь цикл создания
ресурсов; учитывать окно сразу после создания, до возможного отказа renderer.
Освобождать ресурсы в обратном порядке. Передать состояние отказа runtime;
явно решить, допустима ли работа без экранов. Для недоступного accelerated
renderer предусмотреть программный fallback либо понятную ошибку настройки.

Приёмка: имитированный отказ каждого шага создания освобождает предыдущие
окна и подписки; после аварии статус screens становится failed/degraded.

### CR-16. Индивидуальный FPS игнорируется; статический текст рисуется каждый кадр

Места: `karting/modules/screens.py:158,261,270,322`.

По коду выбирается максимальный fps трёх окон и на каждом такте перерисовываются
все. Поэтому настройки 5/15/30 приводят все окна к общему циклу 30 FPS.
Каждый раз заново выполняются font.render, возможное масштабирование текста,
композиция и загрузка всей поверхности в texture. Подписка data.changed — no-op.
При DEBUG по умолчанию пишутся 45 сообщений о кадрах в секунду, даже когда текст
не изменился. Фактическая загрузка CPU на целевом ПК не измерялась.

Рекомендация: deadline каждого окна; кеш surfaces текста и статической нижней
половины по содержимому/размеру; dirty-флаги на изменения данных и страниц.
GIF обновлять при смене его кадра, сохраняя движение процедурных эффектов.
Логировать изменение содержимого/режима, не повторять неизменный кадр постоянно;
при необходимости сделать отдельный frame-trace. FPS валидировать как >0.

Приёмка: разный fps действительно ограничивает каждое окно; одинаковый текст
не рендерится заново каждый кадр; замеры CPU/памяти выполняются с реальными GIF
и одновременно работающим вебом при INFO и DEBUG.

### CR-17. GIF-кеш не ограничен и блокирует все окна при первом декодировании

Место: `karting/modules/screens.py:221`.

По коду все кадры GIF декодируются и масштабируются синхронно в GUI-цикле.
Первая загрузка большого файла задерживает сразу три окна. Память не ограничена:
один RGBA-кадр 320×80 занимает около 100 КиБ без накладных расходов; 1000 кадров —
около 98 МиБ на отдельный кешируемый вариант. Каждый путь/размер создаёт вариант.
Ошибочный путь заносится в failed_gifs до перезапуска: добавление файла позже
не восстанавливает фон автоматически.

Рекомендация: лимиты размера/кадров/памяти, проверка ассетов заранее,
подготовка Pillow-данных вне render-loop и создание SDL-ресурсов в GUI-потоке.
Для поиска кадра использовать бинарный поиск по накопленным длительностям.
Повтор загрузки по изменению mtime либо явной команде, с ограничением частоты.

Приёмка: чрезмерный GIF отклоняется или обрабатывается в пределах бюджета;
один сложный фон не замораживает остальные окна; исправленный файл можно
подхватить без полного перезапуска приложения.

### CR-18. Настройки и запуск зависят от текущего каталога и имеют побочные эффекты

Места: `config.py`, `run.py:15,47`, `run.cmd`, `tests.cmd`,
`karting/modules/screens.py:46`.

По коду пути data/screens/log относительные; run.cmd вызывает относительный
run.py и содержит абсолютный путь к конкретной установке. Импорт run сразу
перенастраивает logging и создаёт runtime с чтением screen-config.
Настройки не имеют общей проверки диапазонов/типов: например fps=0 снимает
обычный лимит Clock.tick, строка messages превращается в кортеж символов.

Рекомендация: main() для запуска и настройки logging; фабрики без побочных
эффектов импорта. Явная база относительных путей — каталог проекта или конфигурации;
batch-скрипты привязать к `%~dp0` с сохранением нужного DATA_FOLDER.
Валидировать размеры, fps, интервалы, порт, списки сообщений и конфликты COM.
Печатать понятную ошибку параметра до старта потоков. Данные гонки state/participants
доступны в store, но показ имён и режимов waiting/paused/finished в интерфейсах
нужно добавить явно, если требуется: сохранение метаданных ещё не их индикация.

Приёмка: запуск из другого cwd использует те же конфиги; импорт фабрики не меняет
журнал приложения; неправильная настройка не приводит к частично запущенной системе.

### CR-19. Реестр COM и Delphi-отправитель требуют согласования с контрактом

Места: `com_port_inventory.py:45,81,94`,
`delphi/KartRecordsSender.pas:91,102,222`.

По коду ID COM содержит VID/PID/serial, но не интерфейс: несколько serial-портов
одного USB-устройства с одинаковым серийным номером получат один ID и одну запись
expected_port. Дубли ID в CSV молча перезаписываются. CSV пишется прямо с усечением
исходного файла: сбой записи может повредить вручную заполненный реестр.

Рекомендация для COM: различать физический device_id и идентификатор его порта/
интерфейса; сигнализировать неоднозначные/дублирующиеся ID, а не выбирать молча.
Для плат без уникального serial сохранить документированное ограничение;
LOCATION не выдавать за идентичность устройства при перестановке USB.
CSV сохранять атомарной заменой и, при необходимости, с резервной копией.

По коду Delphi всегда формирует три объекта рекордов: отсутствующий результат
нельзя передать как null. В снимке нет date/month, необходимых для однозначного
определения периода. Настроены send/receive timeout, но нет явно реализованного
общего deadline операции, включая DNS/connect; синхронный вызов из UI может
задержать приложение. Ответ проверяется поиском подстроки вместо JSON-поля.

Рекомендация для Delphi: признак HasValue, date/month, версия схемы и время
снимка, проверка конечного положительного времени круга. Очередь новейших снимков
и отправка вне UI, ограниченный deadline всей операции, разбор JSON-ответа.
Сохранить совместимость Delphi 7 и проверить реальной сборкой.

Приёмка: два интерфейса устройства не схлопываются в CSV; ошибка записи не
уничтожает реестр; Delphi передаёт null/период и кириллицу, не блокирует UI при
недоступном сервере. Эти сценарии на настоящем железе/компиляторе ещё не проверены.

## P3: сопровождение

### CR-20. Журналирование неполно для диагностики и имеет лишние побочные эффекты

Места: `karting/logging_config.py:18`, `karting/modules/odtemp.py:199`,
`karting/modules/tcp.py:16`, `karting/modules/screens.py:270`, `README.md`.

По коду root.handlers очищаются без явного закрытия прежних handlers, в том числе
при импорте run. ODTEMP не пишет raw ответов в фазе командной инициализации;
TCP disconnect при исключении не гарантирован. README обещает connection lost
на INFO, а реализация пишет WARNING. Такое сообщение видно при INFO, но его
фактическая severity отличается от описания. DEBUG многократно дублирует payload
в источнике, store, событиях и кадрах, включая имена участников.

Рекомендация: конфигурировать журнал только в entrypoint, аккуратно закрывать
собственные handlers; единые переходы состояний с module/source/device/revision.
DEBUG — полученные/отброшенные строки и причины, INFO — рабочие переходы,
WARNING/ERROR — деградация/сбой. Согласовать документацию, убрать неизменные
кадровые повторы. Для персональных данных определить срок хранения/доступ к логам.

Приёмка: по одному журналу понятно, когда модуль потерял связь, начал retry и
получил первое новое значение; повторная настройка не оставляет открытые файлы.

### CR-21. Штатные тесты не покрывают наиболее рискованные жизненные циклы

Места: `features/sources.feature`, `features/screens.feature`,
`features/web.feature`, `features/environment.py`, `tests/`,
`test_tcp_race_contract.py`, `README.md`.

Сценарий ODTEMP watchdog проверяет функцию сравнения времени, не полный цикл
отключения/retry/восстановления. Экранные тесты проверяют planner и Surface,
не создание трёх настоящих Window и освобождение после частичного отказа.
Flask test client не исполняет JavaScript, поэтому не обнаруживает CR-01.
Тест TCP-контракта в корне не входит в документированную команду discover -s tests.
Ошибки cleanup в after_scenario молча игнорируются и могут скрыть утечку ресурса.

Рекомендация: добавить регрессии из пунктов CR-01–CR-19; единая команда должна
запускать все unit/Behave-тесты. Для watchdog/retry использовать управляемые часы
и подменённые устройства, а не ожидание реальных 120/60 секунд. Для гонок потоков
использовать barriers/events, а не случайные sleep. Отдельный браузерный smoke
и opt-in аппаратный/SDL2 smoke на целевом Windows-ПК. Ошибку cleanup делать
видимой, не теряя исходную причину падения сценария.

## Рекомендуемый порядок внедрения

1. **Корректность приёма и представления:** CR-02/03/14, общие модели и валидаторы,
   семантика пустого результата, совместимость со старыми файлами.
2. **Store и события:** CR-04/08/09, immutable snapshots, монотонная revision,
   удаление как изменение, надёжные уведомления. Затем CR-01 — единый веб-polling.
3. **Длительная работа:** CR-05/06/07/10/11/12/13/15 — восстановление источников,
   статусы качества, остановка подключений и очистка частичного запуска.
4. **Конфигурация и интеграция:** CR-18/19 — предсказуемые пути, ID устройств,
   Delphi-контракт. Обновить interface.md/README под фактическое поведение.
5. **Измеренная оптимизация:** CR-16/17/20 — текстовый кеш, per-window FPS,
   бюджет GIF и логов; зафиксировать нагрузку на целевом компьютере.

CR-21 выполнять вместе с каждым исправлением, а не отдельным последним этапом.
Не объединять исправление ядра, всех источников и UI в один непроверяемый патч.

## Предлагаемая структура данных без лишней инфраструктуры

Оставить словарь `category -> immutable DataValue` в памяти. В оболочке категории:
value, source, revision, received_at и quality/status; при необходимости expires_at.
Глобальная revision относится ко всем операциям изменения, включая удаление.
Дата/месяц и время события поставщика остаются внутри domain payload и не
подменяются временем получения. Модулям по-прежнему доступны все категории.

Доменную модель гонки отделить от формы, нужной старому HTML: исходный snapshot
не изменяется, вычисленные поля строятся одной чистой функцией. Правила
ранжирования определить явно: текущая реализация ранжирует по лучшему кругу;
это допустимо для квалификации, но не следует автоматически считать правилами
гонки на дистанцию без отдельного требования.

Для категорий с несколькими производителями договориться о владельце, приоритете
или явном last-write-wins. Сейчас YAML/TCP/serial могут взаимно заменять значения.
Это не обязательно ошибка, но политика должна быть определена и наблюдаема в
source/логах. Повторный одинаковый снимок сегодня меняет revision и уведомляет
подписчиков; «идемпотентность» interface.md относится к итоговому payload, а не
отсутствию повторных событий. Если это важно — добавить dedup/sequence_id.

Постоянное хранение вводить только при необходимости переживать перезапуск.
Для небольшого объёма хватит атомарно сохраняемого валидного JSON-снимка;
после загрузки обязательно перепроверять дату, TTL и статус свежести.

## Минимальные регрессии для Behave

- Участник ещё не завершил круг: число кругов 0, лучший круг отсутствует.
- Неправильный TCP-снимок отклонён, последний валидный снимок сохранён.
- Сбой одного подписчика не останавливает остальные подписки и источник.
- Удаление категории повышает ревизию и уведомляет веб-клиента.
- Обновление между проверкой и ожиданием не теряется.
- ODTEMP: сбой автодетекта → retry → смена COM → первое новое измерение → restored.
- ODTEMP: 120 секунд без измерения → stale; попытки раз в 60 секунд;
  выключение модуля прекращает попытки.
- Файл исчезает во время scan, worker продолжает работу.
- TCP-клиент, подключённый до stop, больше не может записывать данные.
- Второе Pygame-окно не создалось, первое освобождено.
- Рекорд null и рекорд предыдущего периода не выдаются за текущий результат.
- Повторный start/stop не дублирует потоки, stop одного модуля не мешает другим.

Дополнительно вне обычного Behave: браузер исполняет polling без ошибок и лишних
reload; opt-in smoke проверяет реальное железо, SDL2-окна и сборку Delphi 7.
